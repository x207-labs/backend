## B8-F1 (Medium): the edges cannot be recovered after `prune_epoch`
`clearing_applied` of 0.0.13 carries `edge_count` and `edges_hash` only, and `commit_epoch` takes the edges out of the stored proposal (`std::mem::take(&mut proposal.edges)`, `commit.rs:88`). After the commit, `cleared` per pair is readable only from `list_obligations(epoch)`, which reads the pair records. `prune_epoch` removes exactly those pairs and the edge index of a `finalized` epoch, and anyone may call it. So the edges of an epoch exist on chain in a window: from the commit to the first successful `prune_epoch` after `finalize_epoch`. Nothing in the event stream (`clearing_submitted` is a summary too) holds them.

Consequences:
1. A new indexer, or one that was down for more than the window, reads an empty or short list for that epoch. The backend checks the set against `edges_hash` and halts (`IndexerHaltError`), and a halt is permanent: it blocks every later block, not only that epoch. A rebuild is not affected (the edges are kept in `clearing_edges` once read), but a database that never had them cannot be built from the chain alone.
2. The audit trail of what was cleared is gone from the chain for anyone who did not copy it in time. The hash proves a copy; it cannot produce one.
3. Reading at the block height of the event (`call_function` with `block_id`) would work, but needs an archival node, which the near-sandbox, testnet and the Neardata mainnet source do not all give.

Fix options, in the order of cost: (a) the contract keeps the cleared edges in the epoch record until a later explicit step (for example `prune_epoch` refuses while the edges were not published) or keeps a compact list of `cleared` per pair after the prune; (b) a permissionless `publish_cleared(epoch, from_index, limit)` that emits the edges in chunks of at most `MAX_EVENT_ITEMS`, called by the keeper after the commit, so the edges reach the event stream again in separate receipts; (c) the backend reads with `block_id` of the event and fails loudly when the node is not archival. The backend already keeps what it read, so (c) only matters for a late start. Owner: contracts team for (a) and (b), backend team for (c).

## B8-F2 (Low): `get_proposal` `edge_count` is 0 after the commit
`ProposalView.edge_count` is `proposal.edges.len()` (`commit.rs:117`). After the commit `edges` is empty, so a reader of a committed proposal sees `edge_count` 0 next to `committed: true`, although the struct keeps the true `edge_count` (and the event has it). Use `proposal.edge_count`. The test `get_proposal_pages_the_edges_until_the_commit` checks `edges.len()` after the commit and not `edge_count`, which is why it passes.

## B8-F3 (Low): pages of `get_proposal` are not atomic
A reader pages with `from_index` and `limit` (at most 300). A better proposal (higher `cleared_total`) may replace the stored one between two calls, and the second page then belongs to another proposal. The view returns `solver` and `cleared_total` in every page, which lets a careful reader notice, but the order of the edges is the order of submission, not a stable key, and nothing says "start again". Add `edges_hash` of the stored proposal (computed at submit, one hash over the edges the contract already walks) and `submitted_at` to the view, and say in the doc that a change of either restarts the read. The backend does not use `get_proposal` (it reads `list_obligations` after the commit), so it is not affected today.

## B8-F4 (Low): the log size test is not the worst case
`events.rs` builds 64 positions with `role` `debtor` and `status` `due` and amounts of 13 digits. The longest valid entry is `creditor` with `claimable` (8 and 9 characters against 6 and 3): 203 bytes instead of 195, 512 bytes more over 64 entries. Computed with 64 character names and `9999999999999` for `net`, `amount` and `outstanding_debt`: epoch_committed is about 13.36 KB, `clearing_applied` with the largest numbers about 0.45 KB, together about 13.8 KB. That is under the 14.7 KB budget (90 percent of 16,384) and leaves 16 percent, not the 20 percent in the comment (12.6 KB). It holds, with less room than written. The 13 digit bound itself comes from `limit_cap` at most 1e11 (`params.rs` accepts `100_000_000_000`) times at most 64 members; it is a reasoning about `net` and `outstanding_debt`, not an assertion. Use `creditor`/`claimable` in the unit test, and add an assertion in `commit_epoch` (or a sandbox test with real maximum flows) that every amount has at most 13 digits.

## B8-F5 (Info): the canonical bytes match
Checked in the source: `ClearingEdge` serializes `debtor`, `creditor`, `cleared` in that order with `U128` as a decimal string; `PositionEntry` serializes `account_id`, `net` (`I128` as a string), `role`, `status` (`Option`, so `null` and not skipped), `amount`, `outstanding_debt`; the sort is `&str` comparison, which is byte order; edges with `cleared` 0 are dropped before sorting; an empty list is `[]` and its hash is `4f53cda1…b945`, which `commit.rs` asserts. `serde_json::to_string` escapes only control characters, quote and backslash, and account ids contain none. The two Rust tests in `ct099_hash_vectors.rs` take their cases from the same JSON file as the SDK and the backend; the SDK (`edgesHash`, `positionsHash`) and the independent copy in the backend tests both pass every case (run here). Numbers: no sign on unsigned values, no leading zeros, `-0` cannot occur. The three implementations agree on order, number format and empty list.

## B8-F6 (Info): size and the attacker proposal
`clearing_applied` is now a fixed size (the longest case is below 0.5 KB) and `epoch_committed` is bounded by `MAX_MEMBERS` (64) and by the 64 characters of an account id, so no log of `commit_epoch` grows with a proposal any more; the old chunk loop of the edges is gone. `emit_chunked` remains only for `limits_updated` (50 per chunk, at most 64 members) and A2's tests cover `finalize_epoch` with 63 defaults (with the omission line of `settlement.rs`) and a bundle of 64 legs. A proposal can have at most the edges the verifier accepts (300 per transaction), so a solver cannot make a proposal whose commit overflows a log. The replacement rule (a higher `cleared_total` replaces) is unchanged from 0.0.12: an attacker pays gas and storage for each replacement and gains nothing but a delay up to the proposal window, as before. The gas of hashing 300 edges with 64 character names inside `commit_epoch` is what `a_proposal_of_300_edges_can_be_committed` measures; that result was not seen by this review.

## B8-F7 (Info): a breaking change of two events
`clearing_applied` lost `edges`, `chunk`, `chunks`; `epoch_committed` lost `chunk`, `chunks` and gained `position_count`, `positions_hash`. The version of the envelope is 0.0.13, and a reader built for 0.0.12 halts (the SDK parser refuses a higher version) or, if it ignores the version, reads an event with no edges. The order of deployment is: the indexer and SDK that know 0.0.13 first (the backend keeps both forms: 0.0.12 events already stored are replayed as before), then the contract. The testnet read model (`docs/testnet-readmodel.md`) was built from 0.0.12 events and stays valid.

## What is not covered
The sandbox tests of contracts team (`ct099_commit_log_size.rs`) were not run by this review, and the wasm was not inspected. The gas figures, the real size of `epoch_committed` in a receipt, and the claim "a proposal that was accepted can always be committed" rest on those tests.
