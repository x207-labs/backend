# Security review, batch 6 (BE-062): one-time codes of P3 (SD-076, FE-032, AG-030)

Scope, read only: the SDK format `sdk/packages/core/src/code.ts` (SD-076, `4c08146`, with its tests); the page `frontend/src/lib/codeFlow.ts` and `frontend/src/pages/Codes.tsx` (FE-032, `b637598` and the two before it); the agents `agents/scenario/code.ts` and its tests (AG-030, `a07208c`, `a323dc6`). Nothing was changed in the sdk, the frontend or the agents. The backend half (BE-069, BE-070) is by the author of this review and is looked at too, where a finding crosses into it. Main B reviews that half.

Levels as in batch 2: High = money or a proof can be forged by the other party with no cooperation; Medium = a documented guarantee does not hold under a plausible setup; Low = hardening; Info = a limit to write down. Findings marked "run" were reproduced with a throwaway test against the real backend (deleted after); the others are "read from the code".

Checked and found sound: the commitment (`sha256(0x00 ‖ salt ‖ code)` with a random 32 byte salt; the payload splits without ambiguity because the salt has a fixed length; a dictionary of codes without the salt finds nothing, test `TC-SD-076-01b`); the key is sealed to the buyer and the release is signed, so a release for another purchase or another ciphertext is refused (`wrong_purchase`); `createCodeRelease` checks the code against the commitment before it signs; the page keeps the code, the salt and the key only in React state (no `localStorage`, `sessionStorage`, URL, `console` or `history` call in `Codes.tsx` or `codeFlow.ts`), shows the code only after a click, and signs the notices with the purchase id that it compares to the one the user opened (`sameId`); the buyer page recomputes the hash of the listing before the buyer pays (`checkListingToBuy`); the agents print nothing of a code, salt or key (no `console` in `scenario/code.ts`; the audit of `SecretProxy` holds paths and statuses; the error of `HttpCodeBook` carries the message of the server, which never holds the code); the mock book keeps only verdicts (`dump()` is tested); the same code under another salt is not detected from the listing, and the SDK says so.

## B6-F1 (High): a dispute without proof is unconditional, and the code works once
In `purchases.ts` a dispute with `reason` `other` (or `contains_pii`) and no proof goes straight to `disputed`: the voucher stays held, the seller is not paid, and nothing checks the claim (`content_mismatch` is the only reason that is checked, with the proof of cheating). For a file this is the documented answer to a seller who sends a key that cannot be opened (`docs/license.md`: "the buyer disputes other, and the voucher stays held"). For a code the same rule means the buyer can open the code, redeem it at the issuer, and then dispute `other` ("code already used"): the seller gets nothing and the code is gone. The page of the buyer has a button for exactly this (`Dispute: code already used or refused by the issuer`, `disputed`, `other`, `null`) and the text before it tells the buyer to try the code first.
Run: seller lists a checkable code, buyer buys, seller checks and releases the key; the buyer disputes `other` with `proof: null`: `201 {status: "disputed"}`, no voucher.
Nothing in the system can tell this buyer from an honest one whose code was already used: the issuer says `used` and not who used it. The check before the release makes a code that was used earlier fail, but it does not protect the seller afterwards.
Impact: up to the price of the code per purchase, for any code, against the seller; the cap of 20 credit (unverifiable codes) does not limit this, because it is a cap on the buyer's risk, which is the other side.
Fix, in order of cost: (a) say it in ADR-48 and in the page of the seller (the seller bears the risk of a buyer who disputes `other`); (b) reputation: a `disputed` `other` counts against the buyer in BE-053 and an account that disputes more than some share of its purchases is shown on the listing; (c) a real arbiter with a bond (CT-094) for the sale, which needs a path for a one-sided sale that the contract does not have today (see B6-F2); (d) for a checkable issuer that reports the time of redemption, compare it with the time of the release. Owner: Main C (rule), Main B (page text); the decision is the coordinator's.

## B6-F2 (Medium): the arbiter is a name, not a bond
`checkCodeDocument` accepts a non-checkable code of any value when the document names an `arbiter` that is not the seller (`code_over_limit_unbonded` only when there is none). The backend (`codeCheck`) accepts the same. No deal and no bond exists for a sale paid by one voucher: CT-094 locks stakes in `commit_bundle` with an arbiter in the terms of a swap of two. Run: a code of 500 credit that cannot be checked, with `arbiter: citra`, is listed `201`; no deal is created. A checkable code of 5000 credit is listed `201` too (no cap for them at all). The page marks such a listing "with bond" and the warning of the buyer says "seller bond", and the page reads `bond: true` without any arbiter as bonded (`parseCodeListing`). ADR-48 point 2 ("above it a bond is required, CT-094") is therefore not enforced.
Fix: until a bond exists for this kind of sale, apply the cap to every non-checkable code whatever the arbiter says (backend: refuse; SDK: `codeNeedsBond` ignores the arbiter, or the doc field is dropped), and take "with bond" off the pages. Owner: Main C and Main B.

## B6-F3 (Medium): the agent confirms at once
`receiveCode` of the agents checks the delivery and sends `confirmed` in the same call. `confirmed` is what releases the voucher to the seller. The one hour window, which is the only protection of a buyer against a code that does not work (unverifiable codes, and the case of B6-F1 seen from the buyer's side), is skipped. The page of the buyer tells a human to try the code first; the agent has no such step although `MockCodeIssuer.redeem` exists in the same file.
Fix: the agent redeems (or at least asks the issuer, when it has the adapter) before it confirms, and when it cannot, it waits for the window to pass in silence (silence confirms) instead of confirming. Owner: Main B.

## B6-F4 (Low): the delivery is not bound to the listing the buyer looked at
`verifyCodeDelivery` has an optional `doc`: with it the release must carry the hash of that code document, the commitment and the circle. The page (`receiveLicense`, then a comparison with `view.contentHash` of the purchase) and the agents (`receiveCode`) do not pass it. The check that remains is that the content hashes to the commitment of the purchase as the backend reports it. The backend rejects a release whose `content_hash` is not the commitment of the listing (`key_released` checks `r.content_hash === p.content_hash`), so a seller cannot get through with it; a backend that lies could. For agents that confirm without a human this is the only guard.
Fix: pass the code document (rebuilt from the listing the buyer inspected: circle, seller, value, issuer, verifiable, arbiter, nonce, commitment) to `verifyCodeDelivery`. Owner: Main B.

## B6-F5 (Low): a "code" of any size
`createCodeRelease` refuses a code under 8 or over 1024 bytes and with control characters, but a seller who does not use the SDK can commit to any payload. The buyer decrypts the whole content, and `verifyCodeDelivery` returns it as text. The backend accepted any `content_size` up to what a ciphertext may be (256 MiB). A page would hold megabytes in memory, and a terminal that prints the code would print the control characters of the seller.
Fixed in the backend: a release of a code needs `content_size` from 40 to 1056 and `cipher_size` at most `content_size + 64` (`TC-BE-069-13`). Not fixed, Main B: `verifyCodeDelivery` and `splitCodePayload` should refuse a payload over `32 + 1024` bytes and a code with control characters, so that a client that talks to another backend is protected too.

## B6-F6 (Low): the key of the seller is typed
The buyer pastes `ed25519:…` of the seller (`Seller public key`) and the release is checked against it. The page reads the key of the buyer from the contract for the seller's side (`memberOnChain`) but not the key of the seller for the buyer's side. A key copied from the page of the seller, or from the backend, is a key given by the party that can lie. Fix: read `pubkey_voucher` of `view.seller` from the contract and show its fingerprint. Owner: Main B.

## B6-F7 (Low): the label says the code goes nowhere
The field is labelled "Code (not sent anywhere; only its hashed commitment is in the listing)". For a code that can be checked, the page later sends the code and the salt to the backend (it says so in the disclosure of the check). The first text is read before the box "can be checked" is chosen. The code is also typed in a plain text field. Fix: put the exception in the label, and use a masked field with a show button, as the buyer page does for the result. Owner: Main B.

## B6-F8 (Info): the mock is not the book
`MockCodeBook` answers `code_value_over_cap` and `code_format_invalid` (names proposed in the first design) where the real backend answers `code_over_limit_unbonded` and the errors of SD-076; it does not check `content_hash` of the release against the purchase, and its `check` keys the verdict by commitment and cancels with different rules. A scenario that passes against the mock can fail against the real book; `test/code.book.test.ts` (with `HttpCodeBook`) is the one that tells the truth. Keep the mock's errors in step with `backend/docs/code-book.md`.

## B6-F9 (Info): redaction of the key
`SecretProxy.call` (and `ProviderRegistry.redact` in the broker) replaces the exact string of the key in the answer. A provider that echoes it percent-encoded, in base64, in a header, or cut, passes it to the buyer. The risk is the provider's, but the broker could also refuse an answer in which the key, or its first 8 bytes, appears in any common encoding.

## B6-F10 (Info): who paid is not shown to the seller
The seller seals the key to `view.buyer`, which the backend names. The voucher that shows who paid is released only when the purchase is confirmed. A backend that changes `buyer` (to a member with its own key) gets the code. The page does check that the named buyer is an active member with a key on the contract, not that this member is the one who paid. Inherent to the held voucher; write it in ADR-48 as trust in the backend, next to the one for the check.
