# Cross review of batch 1 of the barter catalogue (SD-061, FE-023, AG-023), 2026-11-03

Read as an attacker, against what the contract checks (CT-075, CT-090, CT-092) and what the backend checks (BE-049). No file of `sdk`, `frontend` or `agents` was changed. The tests are in `tests/security-review-batch1.test.ts` (unit tests, no sandbox). A test marked `it.fails` asserts the safe behaviour and passes only while the problem exists; when the code is fixed it fails and must become a plain `it`. Plain tests record a question that was answered "no problem".

## The five questions
| Question | Answer | Tests |
| --- | --- | --- |
| Can the template make a listing whose scope differs from what the escrow checks, so that the buyer pays and the escrow fails? | **No, for the scope itself.** For the eleven inputs (ten kinds, the pool share in both standards) the scope of the grant, the keys of the detail and the arguments of the deposit are the same, with the same contract, token and amount, and the asset type and delivery method match the registry. A buyer pays only when the escrow already holds the asset (`complete_escrow` starts from `held`), so a wrong scope shows as a refused deposit, not as a lost payment. What can still fail after the payment is the transfer to the buyer (a whitelist, a freeze, an unregistered buyer, a fee token); the contract then takes the voucher back. **But** see X1 and X4: a listing can be refused after the asset is already in escrow. | TC-XR1-01, 02, 03, 13 |
| Is `amount`, a decimal or a `token_id` rounded or cut anywhere? | **No rounding or cutting.** Amounts are strings up to u128 and the display is computed on the digits. The form converts "2.5" to the smallest unit with `BigInt`, refuses more fraction digits than the token has, and refuses `1e6`, `1,5`, `+5`, `0x10`. A multi-token amount is not parsed as a number. One thing is not exact: the decimals are read with `Number(text)` (X2) and are the owner's claim (X3). | TC-XR1-04 to 08 |
| Do the RWA warning and the fee-token warning always appear? | **Yes** in the template: the fee warning is in all six kinds that move a fungible amount and in none of the NFT kinds; the registration warning is in all NEP-141 kinds; the RWA rules warning is in every RWA listing whatever the whitelist input. The form lists `template.warnings` as they are. The warning about the **circle's** list of accepted tokens is missing (X4), and nothing says that the decimals were not checked (X3). | TC-XR1-09 to 13 |
| Can a secret get into `detail`? | **Yes, through free text** (X5). The guard looks at the names of the keys, not at the values. | TC-XR1-14 to 16 |
| Are the validation of BE-049 and the templates of SD-061 the same for the ten kinds? | **Yes for what the SDK builds**: all eleven inputs, and the ten inputs of AG-023, pass the backend check when the circle registered the types and whitelisted the RWA token; asset types, kinds and delivery methods agree. They differ on **inputs the SDK cannot know**: the circle whitelist of RWA tokens (X4) and the USDT of the circle (X6). The backend side of X6 is fixed (BE-049, `TC-BE-049-08b`). | TC-XR1-17 to 20 |

## Findings
| # | Where | Problem | Test (`it.fails`) | Suggested fix |
| --- | --- | --- | --- | --- |
| X1 | SDK `tokenId()` | A non-ASCII token id passes the template, but `Listing.detail` must be ASCII. The owner can offer the grant and put the asset in escrow (the contract accepts up to 128 bytes), then the listing is refused: the asset stays in escrow until the grant has expired (`cancel_escrow` is allowed only after `expires_at`). | TC-XR1-03 | Refuse non-ASCII (or any character that makes the detail non-ASCII) in `tokenId` with `bad_token_id`. |
| X2 | Frontend `toAssetInput` | `Number(text)` reads decimals "0x6" as 6 and "1e1" as 10. Nothing is rounded, but another text is read silently. | TC-XR1-07 | Accept decimals only when `/^\d{1,2}$/`. |
| X3 | SDK and form | The display ("2.5 USDC") and the amount come from the decimals and the symbol that the owner typed. Nothing compares them with `ft_metadata` of the token, and no warning says so. A wrong decimals (a slip) lists "2.5 USDC" for 250 units. | TC-XR1-08 | Add a warning now; later an injected check like `checkRwaWhitelist` that reads `ft_metadata`. |
| X4 | SDK warnings, whole order of operations | The backend refuses `rwa:tokenized` unless the circle whitelisted the token; the template knows nothing of it. The form lets the owner do `offer_grant` and the deposit **before** the listing is posted. A refusal of the listing then leaves the token in escrow until the grant has expired. The same holds for any refusal of BE-049 (type not registered in D10, class, quantity). | TC-XR1-13 | Warn; better, post the listing (or a dry-run check of it) **before** the grant and the deposit. A dry-run route of the backend can be added if wanted. |
| X5 | SDK `secret_in_listing` | The guard checks the names of keys. A private key (`ed25519:…`), a password, an API key or a coupon code typed in `name`, `description`, `product`, `label`, `valueInfo` or `rate.source` is written into a listing that everybody can read. | TC-XR1-15, 16 | Scan the values too (keys of an account, `sk_`/`ghp_` tokens, `password=`, long mixed tokens). A heuristic, so keep the warning that a coupon code is never to be written there. |
| X6 | SDK has no input for the USDT of the circle | A `ft`, `lst` or pool-share listing whose token is the USDT of the circle passes the template and the contract refuses its deposit (`ERR_ESCROW_USDT`): it can never be bought. Backend: fixed in BE-049 (`usdtTokenId`). | TC-XR1-20 | Let `buildAssetTemplate` take the USDT of the circle and refuse it. |

Not tested and left as a note: the call of the deposit carries no gas, so the sender's default decides; the sandbox tests used 150 Tgas. A listing may outlive its grant (the template does not return the listing time), so a buyer can match a listing whose grant has expired; the contract refuses the purchase before any payment is registered.
